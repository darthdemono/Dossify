# Local-first lifelog tools for Dossify

## What do Timelinize, ActivityWatch, and OpenLifetracker currently provide?

### Takeaway

Timelinize is the closest architectural neighbour: it ingests heterogeneous historical exports into a local, entity-aware timeline. ActivityWatch is instead a continuously running activity collector, while the closest verified project branded “Open Life Tracker” is a Firebase-backed health-tracking PWA, not a local-first personal-archive compiler. [Timelinize README](https://github.com/timelinize/timelinize#readme) [ActivityWatch FAQ](https://docs.activitywatch.net/en/latest/faq.html) [Life Tracker by Bonn README](https://github.com/AndreaBonn/LifeTrackByBonn#readme)

### Cited Findings

- **Timelinize:** a self-hosted application that imports files and archives from accounts, devices, and applications; it indexes them in SQLite, copies stored data into a date-organised timeline folder, recognises unchanged content on later imports, and presents projections including a classic timeline, map, entity filters, conversations, and media gallery. It explicitly warns that the software and schema are unstable and users may need to recreate timelines after upgrades. [README](https://github.com/timelinize/timelinize#how-it-works) [Importing data](https://timelinize.com/docs/importing-data)
- Timelinize’s in-tree importers currently cover Apple contacts/photos, calendars, email, Facebook, Firefox, Flighty, generic files, GeoJSON/GPX/KML/NMEA location data, GitHub, Gmail, Google Location/Photos/Voice, iCloud, iMessage/iPhone/SMS Backup & Restore, Instagram, media, Strava, Telegram, Twitter, vCard, and WhatsApp. The importer directory is the most direct current capability inventory. [Importer directory](https://github.com/timelinize/timelinize/tree/main/datasources)
- Its persisted model includes provenance-aware data sources and import jobs, plus entities (people, places, organisations, etc.), attributes, items, and relationships. The schema records job state, progress and resumable checkpoints, and acknowledges that imported entities can duplicate and need manual reconciliation. [Schema](https://github.com/timelinize/timelinize/blob/main/timeline/schema.sql) [Schema guide](https://github.com/timelinize/timelinize/wiki/Schema)
- Timelinize processes input on-device and says it neither uploads data nor metadata without explicit consent. Its files are not encrypted; the documented model is single-user OS permissions plus optional whole-disk encryption. [Import privacy and protection](https://timelinize.com/docs/importing-data)
- **ActivityWatch:** a free, open-source automated time tracker for Windows, macOS, Linux, and Android. Its built-in collection records active applications/window titles and keyboard/mouse-derived AFK state; browser extensions can collect active tab titles and URLs. [FAQ](https://docs.activitywatch.net/en/latest/faq.html) [Project README](https://github.com/ActivityWatch/activitywatch#about)
- ActivityWatch has a local server that stores and retrieves per-source “buckets”; watchers, importers, and observers write through a REST API, and the hosted web UI queries the same API. It has dashboard, timeline, activity-browser, raw-data, and query-explorer interfaces. [Architecture](https://docs.activitywatch.net/en/latest/architecture.html) [Project README](https://github.com/ActivityWatch/activitywatch#server)
- Its data model is deliberately small: bucket metadata identifies a source/client/host/type; each event is a UTC timestamp, duration, and flexible JSON data object. Heartbeats merge adjacent same-data events inside a pulse window to reduce storage and I/O. [Buckets and events](https://github.com/ActivityWatch/docs/blob/master/src/buckets-and-events.rst)
- Documented third-party importers include iCalendar/Google Calendar, SmarterTime, macOS Screen Time, WakaTime, Last.fm exports, Lifecycle location exports, and Foqos exports. Raw data can be exported per bucket or across buckets as JSON through the web UI or REST API. [Importers](https://docs.activitywatch.net/en/latest/importers.html) [Exporting data](https://docs.activitywatch.net/en/latest/features/exporting-data.html)
- ActivityWatch stores its data in a local SQLite database and does not itself send it to a cloud service. Its optional desktop sync stages database files in a user-selected sync directory and relies on an external file-sync tool; Android sync remains limited and disabled by default. The project also documents material security limitations, including no API authentication on multi-user systems and no current security audit. [FAQ](https://docs.activitywatch.net/en/latest/faq.html) [Syncing](https://docs.activitywatch.net/en/latest/syncing.html) [Security](https://docs.activitywatch.net/en/latest/security.html)
- **OpenLifetracker name resolution:** searches did not identify an independent official project exactly named “OpenLifetracker.” The closest verified use of the exact branding is the “OPEN LIFE TRACKER” link in the public Life Tracker by Bonn repository; its README states that application source is private, so its implementation cannot be independently audited. [Brand link and license statement](https://github.com/AndreaBonn/LifeTrackByBonn#author-and-license)
- That Open Life Tracker is a health PWA for manual health logs plus Google Fit synchronisation, trends/charts, goals, and CSV exports. It uses Firebase Authentication, Firestore, Cloud Functions and Hosting, and describes cloud-synchronised, per-user data protected by Firebase rules, not filesystem-owned local records. [Features and Google Fit](https://github.com/AndreaBonn/LifeTrackByBonn#how-to-use) [Architecture, export, and privacy](https://github.com/AndreaBonn/LifeTrackByBonn#technologies)

### Inferences

- Treat Timelinize as a reference for archival ingestion and browse-time projections, not as a drop-in storage layer: its canonical database is the source of truth, whereas Dossify’s stated product boundary is a compiler that preserves a human-readable Markdown journal. This preserves Dossify’s reviewability and manual-writing boundary while borrowing only durable patterns. [Timelinize schema](https://github.com/timelinize/timelinize/blob/main/timeline/schema.sql) [Timelinize README](https://github.com/timelinize/timelinize#how-it-works)
- Treat ActivityWatch as an optional upstream producer rather than functionality to subsume. Its best output for Dossify would be a bounded daily summary from exported canonical events, because raw minute-level window/tab telemetry is both probabilistic and sensitive. [Canonical-event guidance](https://github.com/ActivityWatch/docs/blob/master/src/examples/working-with-data.rst) [Accuracy caveat](https://docs.activitywatch.net/en/latest/faq.html)
- Open Life Tracker contributes useful health-dashboard ideas, but its Firebase account/cloud and bidirectional Google Fit model conflicts with the requested private-configurable compiler boundary. [Life Tracker architecture](https://github.com/AndreaBonn/LifeTrackByBonn#technologies)

### Gaps

- “OpenLifetracker” is ambiguous. This note evaluates the closest verified exact branding, Open Life Tracker / Life Tracker by Bonn. If a different repository or URL was intended, its name, architecture, and current capabilities need re-checking against that primary source before design conclusions are drawn. [Verified project README](https://github.com/AndreaBonn/LifeTrackByBonn#readme)
- Timelinize’s repository advertises many importers, but its public documentation does not provide a stable compatibility matrix with exact source-export versions. Adapter feasibility for a particular private export should therefore be established from the specific importer code and fixture tests, not inferred from the directory name alone. [Importer directory](https://github.com/timelinize/timelinize/tree/main/datasources)

## Which import, data-model, and timeline-rendering patterns are worth adopting?

### Takeaway

Adopt a thin, explicit intermediate-event contract with provenance, idempotency, and source-specific adapters; keep Markdown as the reviewed output. For presentation, add derived, read-only timelines or summaries only after the compiler can emit stable source-linked events. [Timelinize import flow](https://github.com/timelinize/timelinize#how-it-works) [ActivityWatch data model](https://github.com/ActivityWatch/docs/blob/master/src/buckets-and-events.rst)

### Cited Findings

- Timelinize imports original archives without requiring pre-extraction, recursively recognises supported files and can traverse archives to form an import plan; it treats input files as read-only and copies data into the timeline. [Tutorial](https://timelinize.com/docs/tutorial) [Importing data](https://timelinize.com/docs/importing-data)
- Timelinize records jobs with a type, configuration, duplicate-prevention hash, lifecycle state, progress, status message, checkpoint and repeat/parent-job fields. [Schema](https://github.com/timelinize/timelinize/blob/main/timeline/schema.sql)
- ActivityWatch’s bucket/event separation allows source-specific JSON schemas without forcing every collector into one wide table. The project recommends one bucket per watcher and host, and its event type identifies the expected event-data shape. [Buckets and events](https://github.com/ActivityWatch/docs/blob/master/src/buckets-and-events.rst)
- ActivityWatch’s canonical-event query layer combines raw source events with AFK handling, categorisation, device priority and time summarisation before its UI or most downstream analysis consumes them. [Working with ActivityWatch data](https://github.com/ActivityWatch/docs/blob/master/src/examples/working-with-data.rst)
- Timelinize’s timeline UI combines types and time segments for day reconstruction, and its other projections reuse the same indexed data: map, entities, conversations and gallery. [Timelinize README screenshots and descriptions](https://github.com/timelinize/timelinize#screenshots)

### Inferences

- **Adopt an adapter contract, not a universal scraper.** Each Dossify adapter should parse only a locally supplied export or explicitly configured local record into a common internal fact with: provider/adapter ID, source locator, source record ID or content hash, observed time plus timezone/precision, event type, structured values, display text, and privacy/retention flags. This carries forward Timelinize’s source-and-job provenance and ActivityWatch’s source-scoped flexible event payloads while leaving Markdown generation as the final stage. [Timelinize schema](https://github.com/timelinize/timelinize/blob/main/timeline/schema.sql) [ActivityWatch data model](https://github.com/ActivityWatch/docs/blob/master/src/buckets-and-events.rst)
- **Adopt an import manifest and resumable status, in a private workspace.** Record input fingerprints, adapter version, parse count, skipped/duplicate count, warning count, start/end time, and a checkpoint when an archive is large. On rerun, append only facts whose stable source ID or canonical-content hash is unseen. This is an implementation recommendation derived from Timelinize’s duplicate-aware repeat imports and explicit job/checkpoint model. [Timelinize README](https://github.com/timelinize/timelinize#how-it-works) [Timelinize schema](https://github.com/timelinize/timelinize/blob/main/timeline/schema.sql)
- **Add a two-layer pipeline: raw facts, then deterministic daily projection.** Preserve adapter output for diagnostics and regenerate summaries, grouped sections, and chronological Markdown from those facts. Where events overlap, aggregate first and render once. This follows ActivityWatch’s raw-versus-canonical separation and makes a rule change reproducible without rewriting an external source. [Working with ActivityWatch data](https://github.com/ActivityWatch/docs/blob/master/src/examples/working-with-data.rst)
- **Use a source-native identity key plus observed display text.** Only link records to a configured person when the configured provider-specific identifier matches; otherwise render the observed label or uncertainty. Timelinize’s entity reconciliation need demonstrates why cross-source automatic identity merging must remain reviewable rather than irreversible. [Timelinize schema](https://github.com/timelinize/timelinize/blob/main/timeline/schema.sql)
- **Make timeline rendering a projection, not a second datastore.** A future local HTML/Markdown dashboard can offer date-range filters, type filters, a day view, compact category totals, and links back to journal anchors or source files. Timelinize demonstrates the value of multiple views over one index; Dossify should start with the low-risk day timeline and source links before maps, conversation views, or media galleries. [Timelinize README](https://github.com/timelinize/timelinize#screenshots)
- **Provide an explicit, bounded ActivityWatch bridge.** Parse exported JSON or query a user-run local instance only when enabled, retain the source bucket and query definition, and emit a day-wide coding/app-category summary rather than every title/URL. ActivityWatch makes complete-bucket JSON export available, while its own guidance recommends aggregating and redacting locally before external model access. [Exporting data](https://docs.activitywatch.net/en/latest/features/exporting-data.html) [Working with ActivityWatch data](https://github.com/ActivityWatch/docs/blob/master/src/examples/working-with-data.rst)

### Gaps

- No primary source establishes a public, versioned interchange format shared by these three tools. Dossify should define its own small private intermediate schema and version it, rather than promise compatibility with an unspecified “lifelog” format. [Timelinize schema](https://github.com/timelinize/timelinize/blob/main/timeline/schema.sql) [ActivityWatch data model](https://github.com/ActivityWatch/docs/blob/master/src/buckets-and-events.rst) [Life Tracker export](https://github.com/AndreaBonn/LifeTrackByBonn#technologies)
- There is no evidence that ActivityWatch’s categories or Timelinize’s entity matching fit Dossify’s existing private rules without a deliberate mapping. Any bridge needs fixtures representing ambiguous identities, duplicate records, missing timezone data, and partially rerun adapters. [ActivityWatch accuracy guidance](https://docs.activitywatch.net/en/latest/faq.html) [Timelinize schema](https://github.com/timelinize/timelinize/blob/main/timeline/schema.sql)

## What would be poor fits for Dossify's Markdown-first, private-configurable compiler model?

### Takeaway

Dossify should avoid becoming a persistent surveillance service, a cloud account product, or a second canonical personal-data database. The valuable design boundary is “parse local evidence, generate a reviewable journal block, preserve manual writing,” with optional read-only projections around it. [ActivityWatch architecture](https://docs.activitywatch.net/en/latest/architecture.html) [Timelinize import model](https://timelinize.com/docs/importing-data)

### Cited Findings

- Timelinize copies imports into its own timeline repository and makes the SQLite database its source of truth; it also currently warns users about schema churn and potentially recreating timelines. [Timelinize README](https://github.com/timelinize/timelinize#how-it-works) [Schema guide](https://github.com/timelinize/timelinize/wiki/Schema)
- ActivityWatch’s normal operation depends on continuously running watchers, a local server, local REST API, and a stored time-series database. Its window and browser data can include application names, window titles, page titles and URLs; it cautions that activity statistics are estimates, not objective truth. [Architecture](https://docs.activitywatch.net/en/latest/architecture.html) [Project README](https://github.com/ActivityWatch/activitywatch#about) [FAQ](https://docs.activitywatch.net/en/latest/faq.html)
- ActivityWatch has documented local-API and host-security limits, including no API authentication for multi-user systems and a Firefox extension-origin caveat. [Security](https://docs.activitywatch.net/en/latest/security.html)
- Open Life Tracker requires an account, stores data in Firebase services, automatically syncs across devices, and supports Google Fit bidirectional synchronisation and Telegram reports. [Life Tracker setup and sync](https://github.com/AndreaBonn/LifeTrackByBonn#how-to-use) [Life Tracker architecture](https://github.com/AndreaBonn/LifeTrackByBonn#technologies)

### Inferences

- **Do not replace Markdown with a SQLite-first canonical journal store.** An internal cache or import manifest is useful, but making it authoritative would add a migration/backup/recovery product and move Dossify away from an inspectable file-based journal. Timelinize’s own schema-reset warning illustrates that cost. [Timelinize README](https://github.com/timelinize/timelinize#how-it-works) [Timelinize schema guide](https://github.com/timelinize/timelinize/wiki/Schema)
- **Do not ship always-on window, browser, keyboard, microphone, or location collection as Dossify core.** If an owner wants that telemetry, ActivityWatch or a similar collector should remain an optional, separately configured source. Dossify can compile an intentionally narrow export/summarisation of it, with redaction rules and source citation. [ActivityWatch project scope](https://github.com/ActivityWatch/activitywatch#about) [ActivityWatch security](https://docs.activitywatch.net/en/latest/security.html)
- **Do not add accounts, Firebase-style backend ownership, cloud sync, OAuth-driven bidirectional writes, push notifications, or Telegram reporting.** These features expand the trust boundary from local compilation to credential storage, network availability, remote data ownership and security operations. Open Life Tracker is evidence that such a product is viable, but it is a different product category. [Life Tracker architecture and privacy](https://github.com/AndreaBonn/LifeTrackByBonn#technologies)
- **Do not silently auto-merge people, sources, or duplicate events.** Retain the configured provider identity, original locator and match confidence; make destructive reconciliation a visible private-rule decision. Timelinize itself notes that source-specific entities can duplicate and may need manual reconciliation. [Timelinize schema](https://github.com/timelinize/timelinize/blob/main/timeline/schema.sql)
- **Do not start with maps, social conversation graphs, media copies, health coaching, goal systems, or predictive correlations.** They need large durable stores, richer sensitive-data policies, and interaction design beyond a journal compiler. A read-only day timeline and source-linked summaries offer most of the retrieval benefit at much lower product and privacy cost. This priority follows the breadth of Timelinize’s archive UI and Open Life Tracker’s domain-specific health features. [Timelinize README](https://github.com/timelinize/timelinize#screenshots) [Life Tracker features](https://github.com/AndreaBonn/LifeTrackByBonn#key-features)

### Gaps

- No user research in the cited projects establishes which visual projection Dossify users would value most. Validate a minimal read-only daily timeline against real private-workspace output before committing to a dashboard, and keep the Markdown journal as the acceptance artifact. [Timelinize UI status](https://github.com/timelinize/timelinize#screenshots)
- The exact encryption, retention, and backup policy for any new Dossify private cache is a product decision. Neither local-first label alone guarantees protection: Timelinize documents no timeline encryption, and ActivityWatch notes that local database access or same-host malware defeats its model. [Timelinize import privacy](https://timelinize.com/docs/importing-data) [ActivityWatch security](https://docs.activitywatch.net/en/latest/security.html)
