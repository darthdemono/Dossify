# Dossify adapter architecture

## Python packaging entry points for independently shipped adapters

### Takeaway

Use one PyPA entry-point group, `dossify.adapters`, as the discovery mechanism for separately installed provider packages, but keep the entry point deliberately narrow: it returns an adapter factory or a manifest-bearing object. Entry points solve discovery and distribution identity, not compatibility negotiation, configuration, permissions, isolation, or reproducibility; those must be explicit Dossify contracts.

### Cited Findings

- PyPA defines entry points as a way for an installed distribution to advertise components that other code can discover and use. The distribution supplies a group, a name, and an importable object reference; consumers define the expected interface. [PyPA entry-points specification](https://packaging.python.org/en/latest/specifications/entry-points/)
- PyPA’s plugin guide lists naming conventions, namespace packages, and package metadata as the three automatic discovery approaches. It shows package-metadata discovery through `[project.entry-points.'myapp.plugins']` and `importlib.metadata.entry_points(group='myapp.plugins')`. [PyPA plugin-discovery guide](https://packaging.python.org/en/latest/guides/creating-and-discovering-plugins/)
- PyPA recommends that a consumer creating a group use a name starting with a PyPI name it owns followed by a dot, which supports `dossify.adapters`; entry-point names must only be unique within a distribution, and the consumer chooses the result when different distributions use the same name. [PyPA entry-points specification](https://packaging.python.org/en/latest/specifications/entry-points/)
- The standard-library API returns `EntryPoint` objects with `name`, `group`, `value`, and `load()`; current supported selection is `entry_points(group=..., name=...)`. It also documents the shape changes across Python/backport versions, so Dossify should use the selection API rather than historical dictionary indexing. [Python `importlib.metadata` documentation](https://docs.python.org/3/library/importlib.metadata.html)
- An `EntryPoint` exposes the supplying distribution as `.dist`, but the standard library explicitly says entry points cannot currently be queried by a `dist` filter because distributions do not compare equal. [Python `importlib.metadata` documentation](https://docs.python.org/3/library/importlib.metadata.html)
- Entry-point extras are a legacy facility; PyPA says new publishing tools need not support them and consumers may ignore them. Adapter dependencies therefore belong in normal package dependencies or optional extras documented by the adapter, not in the entry-point value. [PyPA entry-points specification](https://packaging.python.org/en/latest/specifications/entry-points/)

### Inferences

- Define the public packaging surface as one installed package per provider, for example `dossify-adapter-dayone`, with a stable entry-point declaration such as `dayone = "dossify_dayone:adapter"`. This makes third-party adapters independently installable and discoverable while avoiding a Dossify-maintained central import registry. The recommendation follows PyPA’s metadata-discovery model and naming guidance. [PyPA plugin-discovery guide](https://packaging.python.org/en/latest/guides/creating-and-discovering-plugins/); [PyPA entry-points specification](https://packaging.python.org/en/latest/specifications/entry-points/)
- Make the Dossify entry-point name the canonical provider slug and reject duplicate slugs deterministically, reporting both supplying distribution names and versions. The standard leaves cross-distribution conflict handling to the consumer, so silent winner selection would be an application policy rather than a packaging guarantee. [PyPA entry-points specification](https://packaging.python.org/en/latest/specifications/entry-points/)
- Discover first, then load only selected adapters. Since `load()` resolves the advertised Python object, installation plus selection should be treated as trust decisions: an in-process adapter is trusted code, not a sandboxed integration. This is an inference from the standard API’s object-resolution behaviour. [Python `importlib.metadata` documentation](https://docs.python.org/3/library/importlib.metadata.html)
- Do not use package-name scanning or namespace-package enumeration as Dossify’s public extension mechanism. They are valid PyPA approaches, but metadata entry points express intent without importing or scanning every matching top-level package and give Dossify an explicit group boundary. [PyPA plugin-discovery guide](https://packaging.python.org/en/latest/guides/creating-and-discovering-plugins/)
- Pin Dossify’s minimum Python version and test that exact entry-point selection path. If older Python support is required, use the documented `importlib_metadata` backport compatibility boundary rather than custom version-dependent discovery code. [PyPA plugin-discovery guide](https://packaging.python.org/en/latest/guides/creating-and-discovering-plugins/); [Python `importlib.metadata` documentation](https://docs.python.org/3/library/importlib.metadata.html)

### Gaps

- Packaging standards deliberately do not define an adapter manifest, version negotiation, safe execution, or a provider permission model. Dossify must publish those application-level rules itself; there is no PyPA standard to adopt wholesale. [PyPA entry-points specification](https://packaging.python.org/en/latest/specifications/entry-points/)

## Relevant Pluggy, Pydantic, and JSON Schema patterns

### Takeaway

Keep the first adapter boundary as a small versioned typed protocol and use Pydantic models as the canonical validation and schema source. Pluggy is useful later for host-owned multi-party lifecycle hooks, validation, blocking, and tracing, but it should not replace the provider protocol or become a required dependency for a single-adapter-per-provider design.

### Cited Findings

- Pluggy hook specifications validate matching hook implementations at registration; its `check_pending()` can fail unknown non-optional hooks, and implementations may accept fewer arguments than a specification, permitting additive hook parameters. [Pluggy documentation](https://pluggy.readthedocs.io/en/latest/)
- Pluggy can load setuptools entry points, block plugins by name, inspect registered plugins, and expose a tracing facility. [Pluggy API reference](https://pluggy.readthedocs.io/en/latest/api_reference.html)
- Pluggy’s `firstresult=True` hooks stop after the first non-`None` result, while historic hooks can replay a previous call to a late-registered implementation that cannot return a result to the original caller. [Pluggy documentation](https://pluggy.readthedocs.io/en/stable/)
- `pydantic-settings` supplies `BaseSettings` for typed settings loaded from environment variables and secrets files; direct initializer arguments can override values, which is useful for tests. [Pydantic Settings documentation](https://docs.pydantic.dev/latest/concepts/pydantic_settings/)
- Pydantic documents a source-priority order and permits an application to replace or add settings sources via `settings_customise_sources`; the returned order controls priority. [Pydantic Settings documentation](https://docs.pydantic.dev/latest/concepts/pydantic_settings/)
- Unknown environment variables are ignored even with `extra='forbid'`; a misspelled environment name can therefore leave a default in effect. Pydantic distinguishes this from unknown keys that reach a matched nested model, where `extra='forbid'` can produce a validation error. [Pydantic Settings documentation](https://docs.pydantic.dev/latest/concepts/pydantic_settings/)
- Pydantic generates JSON-Schema-Draft-2020-12-compliant schemas. `BaseModel.model_json_schema()` and `TypeAdapter.json_schema()` return JSON-serializable schema dictionaries, and the generation process can be customized. [Pydantic JSON Schema documentation](https://docs.pydantic.dev/latest/concepts/json_schema/)
- JSON Schema Draft 2020-12 defines vocabularies and meta-schemas; a required unknown vocabulary means an implementation must refuse to process that schema. Its validation specification also says `format` is annotation by default and recommends application semantic validation rather than relying on it as an assertion. [JSON Schema Core](https://json-schema.org/draft/2020-12/json-schema-core); [JSON Schema Validation](https://json-schema.org/draft/2020-12/json-schema-validation)

### Inferences

- Publish a tiny `dossify_adapter_api` package containing Pydantic request/result/config models and a `Protocol` or abstract `Adapter` interface, separately versioned from the CLI. An adapter exposes `manifest()`, `config_model()`, `validate_config()`, `plan()`, `execute()`, and optionally `cache_key_parts()`. Validate all values crossing this boundary before use. Pydantic’s model validation and schema generation make one typed definition available both at runtime and as a distributable contract. [Pydantic JSON Schema documentation](https://docs.pydantic.dev/latest/concepts/json_schema/); [Pydantic Settings documentation](https://docs.pydantic.dev/latest/concepts/pydantic_settings/)
- Make `AdapterManifest` machine-readable and required before configuration or execution: `provider_id`, `display_name`, adapter distribution/version, `adapter_api` compatibility range, `config_schema_version`, supported capabilities, requested permissions, deterministic-output declaration, and cache-contract version. The added version fields are an application inference that turns the packaging discovery fact into an explicit compatibility handshake. [PyPA entry-points specification](https://packaging.python.org/en/latest/specifications/entry-points/)
- Treat Pydantic `BaseSettings` as host configuration plumbing only. For each adapter, validate the selected provider block with its Pydantic model, set `extra='forbid'` for configuration-file data, and pass a redacted immutable settings object to the adapter. Do not claim that `extra='forbid'` alone catches typoed environment variables, because Pydantic documents that unmatched environment variables are ignored. [Pydantic Settings documentation](https://docs.pydantic.dev/latest/concepts/pydantic_settings/)
- Export every public adapter config model to a checked-in Draft 2020-12 schema with explicit `$schema`, a stable `$id` containing the provider and config-schema version, examples that contain no secrets, and a test that regenerated schema equals the committed schema. Pydantic supports Draft 2020-12 output and JSON Schema provides the dialect/vocabulary mechanism for stable processing expectations. [Pydantic JSON Schema documentation](https://docs.pydantic.dev/latest/concepts/json_schema/); [JSON Schema Core](https://json-schema.org/draft/2020-12/json-schema-core)
- Use JSON Schema for portable structural validation and documentation, then preserve Pydantic validation for semantic constraints and cross-field checks. In particular, do not make security or provider correctness depend solely on `format`, because Draft 2020-12 treats it as annotation unless the assertion vocabulary is intentionally required and implemented. [JSON Schema Validation](https://json-schema.org/draft/2020-12/json-schema-validation)
- Defer Pluggy until Dossify needs several independent listeners around a host lifecycle event, such as `dossify_before_compile`, `dossify_after_compile`, or audit reporting. At that point add hookspecs before registration and call `check_pending()` in startup/tests. Do not model a provider’s main `plan` or `execute` result as a fan-out hook, because compilation needs one selected adapter and an explicit result rather than arbitrary aggregation or `firstresult` ordering. The latter is an application design inference informed by Pluggy’s 1:N hook and first-result mechanics. [Pluggy API reference](https://pluggy.readthedocs.io/en/latest/api_reference.html); [Pluggy documentation](https://pluggy.readthedocs.io/en/stable/)

### Gaps

- Pydantic-generated schemas describe model shape, not all runtime facts such as an OAuth credential’s continuing validity, remote provider availability, or whether a path is authorized. Those need adapter preflight checks and core-owned authorization enforcement.
- Pluggy validates declared hook signatures, not the semantic meaning, determinism, or permission use of an adapter result. Those guarantees need Dossify fixture and integration tests. [Pluggy documentation](https://pluggy.readthedocs.io/en/latest/)

## Incremental Dossify provider contract, safety model, cache, and fixture tests

### Takeaway

Introduce the system in four compatible increments: a core-owned typed contract and built-in adapters; entry-point discovery and manifests; plan-first permissions and cache ownership; then a public conformance suite. The core must own all side-effecting capabilities and cache identity, so an adapter declares what it needs but cannot self-authorize or silently turn a dry run into a write.

### Cited Findings

- Entry-point metadata gives Dossify a provider name, object reference, and supplying distribution information, but the packaging specification assigns collision handling and the expected object interface to the consumer. [PyPA entry-points specification](https://packaging.python.org/en/latest/specifications/entry-points/); [Python `importlib.metadata` documentation](https://docs.python.org/3/library/importlib.metadata.html)
- Pydantic can create a portable JSON Schema from a model, including Draft 2020-12 output, while settings sources can be customized and inspected in priority order. [Pydantic JSON Schema documentation](https://docs.pydantic.dev/latest/concepts/json_schema/); [Pydantic Settings documentation](https://docs.pydantic.dev/latest/concepts/pydantic_settings/)
- Draft 2020-12 specifies standard validation output formats and recommends output that can be serialized to its JSON data model, supporting a stable JSON plan/diagnostic artifact. [JSON Schema Core](https://json-schema.org/draft/2020-12/json-schema-core)
- Pluggy can be used for host-level tracing, plugin inspection, and blocking, but its loading API remains an entry-point loader rather than a provider contract. [Pluggy API reference](https://pluggy.readthedocs.io/en/latest/api_reference.html)

### Inferences

- **Increment 1, no public plugins:** define the `dossify_adapter_api` data-only models and one in-tree adapter behind the same interface. `CompileRequest` includes normalized source identity, time-zone/locale policy, target format, run mode, and a deterministic clock; `CompileResult` includes normalized entries, attachments by content hash, warnings/errors, provenance, and a `CacheDirective`. Persist only JSON-safe values. Pydantic can validate these objects and emit the public structural schemas. [Pydantic JSON Schema documentation](https://docs.pydantic.dev/latest/concepts/json_schema/)
- **Increment 2, distribution boundary:** add `dossify.adapters` entry-point discovery, load only a user-selected provider, read its manifest, validate core/API compatibility before accepting configuration, and present a `dossify adapters doctor` report with slug, distribution/version, API range, schema IDs, requested permissions, and load/config errors. This converts the entry-point metadata mechanism into a supportable compatibility boundary. [PyPA plugin-discovery guide](https://packaging.python.org/en/latest/guides/creating-and-discovering-plugins/); [Python `importlib.metadata` documentation](https://docs.python.org/3/library/importlib.metadata.html)
- **Increment 3, capabilities and permissions:** distinguish a manifest’s *capabilities* (for example `journal.read`, `attachment.read`, `network.fetch`, `oauth.refresh`, `cache.validator`) from its *requested permissions* (scoped source roots, approved hostnames, secret identifiers, and whether writes are ever supported). The core computes `effective_permissions = user_grant ∩ adapter_request ∩ command_policy`, records it in provenance, and injects only scoped facades such as `JournalReader`, `NetworkClient`, and `SecretResolver`. An adapter never receives raw filesystem, process, or global settings access through the contract. This is necessary because entry-point loading resolves Python objects in-process; it is a least-authority application design inference, not protection from malicious installed Python code. [Python `importlib.metadata` documentation](https://docs.python.org/3/library/importlib.metadata.html)
- **Plan-first dry runs:** `plan(request, context)` must return a canonical `ExecutionPlan` containing ordered intended reads, network requests (method, canonical URL, non-secret header names), proposed output identifiers/content hashes when calculable, cache action, and required permissions. `execute(plan, context)` accepts a core-issued plan ID; in `--dry-run`, the core calls only `plan`, writes the JSON plan and no provider output/cache mutation, and denies facades capable of mutation. This makes dry-run reviewable and testable rather than a convention inside each adapter. JSON Schema’s standardized JSON-oriented output supports a durable plan artifact. [JSON Schema Core](https://json-schema.org/draft/2020-12/json-schema-core)
- **Cache ownership and invalidation:** keep cache read/write in core. Key a compiled result by canonical request plus `provider_id`, adapter distribution name/version, adapter API version, config-schema version, canonical redacted config hash, input fingerprints (content hash or provider revision/ETag), target/compiler version, and cache-contract version. Require `CacheDirective` to state `reusable`, expiry/TTL if any, and validators observed; invalidate on any key change, permission-scope reduction, explicit refresh, or failed revalidation. This is an application inference that makes independently released adapter behaviour part of cache identity rather than an undocumented implementation detail. The distribution provenance is available from entry-point metadata. [Python `importlib.metadata` documentation](https://docs.python.org/3/library/importlib.metadata.html)
- **Reproducible provider contract:** require stable ordering, UTC/RFC 3339 timestamps or an explicitly supplied zone policy, normalized Unicode/text rules, no hidden current-time/randomness, and a provenance record containing adapter/package versions, input fingerprints, permission grant ID, plan hash, cache decision, and redacted config hash. If a provider cannot be deterministic, it sets `deterministic_output=false` and returns a source revision/observed-at value; core then disables cache reuse by default. This is an application-level reproducibility policy, with Pydantic/JSON Schema supplying the serializable contract format. [Pydantic JSON Schema documentation](https://docs.pydantic.dev/latest/concepts/json_schema/); [JSON Schema Core](https://json-schema.org/draft/2020-12/json-schema-core)
- **Increment 4, public adapter conformance suite:** ship a versioned `dossify-adapter-contract-tests` package and a fixture archive per provider. Each fixture has sanitized config, immutable input files or recorded HTTP responses, expected manifest/config-schema identifiers, expected canonical plan JSON, expected normalized result JSON, expected provenance/cache directive, and an explicit fixture format version. Test discovery, duplicate-slug failure, API-range rejection, invalid/unknown config fields, denied permission, dry-run’s no-mutation guarantee, cache hit/miss/invalidation, and deterministic byte-for-byte canonical output. Use Pydantic models and the exported Draft 2020-12 schemas to validate both fixture input and output. [Pydantic JSON Schema documentation](https://docs.pydantic.dev/latest/concepts/json_schema/); [JSON Schema Validation](https://json-schema.org/draft/2020-12/json-schema-validation)
- **Compatibility policy:** allow additive optional fields and capabilities in a minor adapter API release, reserve a major API version for changed semantics or required fields, and preserve old fixture suites until their supported API range ends. This borrows Pluggy’s useful additive-argument evolution principle while applying it to explicit data models, where schema/version tests can detect semantic drift. [Pluggy documentation](https://pluggy.readthedocs.io/en/latest/); [Pydantic JSON Schema documentation](https://docs.pydantic.dev/latest/concepts/json_schema/)
- **Public safety baseline:** document that third-party adapters run as trusted local Python code. Permissions are guardrails for well-behaved adapters and accidental overreach; a real untrusted-adapter boundary would require a separate process with OS/container permissions and a serialized protocol, which should be a later, distinct design decision. The distinction follows from entry-point `load()` resolving provider code into the current Python process. [Python `importlib.metadata` documentation](https://docs.python.org/3/library/importlib.metadata.html)

### Gaps

- The requested scope does not identify Dossify’s supported Python versions, source-provider protocols, data-sensitivity classification, or existing compilation cache. Those facts determine the exact API version range, capability vocabulary, secret backend, cache validators, and whether a subprocess boundary is worth the complexity.
- No public standard defines journal-provider fixtures, permission semantics, or cache invalidation for this application class. The proposed terms should therefore be published as Dossify’s own versioned specification and exercised by the conformance suite before external adapters are invited.
