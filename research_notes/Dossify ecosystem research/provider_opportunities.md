# Provider opportunities for Dossify

Research scope: concrete, privacy-respecting sources for Dossify's local journal compiler, checked 03-10-2026. “Confirmed” below means the vendor/project documents the interface. A ranking is a product recommendation, not a claim that a particular private installation has the service or data enabled.

## Which official export/API/plugin surfaces are stable enough to target?

### Takeaway

Prioritise local exports and local-server reads before any OAuth integration: ActivityWatch, Nextcloud Activity/WebDAV/CalDAV, Immich metadata, and Google Takeout are the best fit for Dossify’s existing offline boundary. Add remote OAuth only where an export is materially worse, and make every networked adapter explicitly opt-in.

### Cited Findings

- **P0 — ActivityWatch local export/REST adapter.** ActivityWatch documents a REST datastore with bucket, event, heartbeat, and query APIs, plus JSON export of individual buckets or complete datasets from the UI or REST API. Its documented event model has an ISO-8601 timestamp, duration, and source-defined JSON payload, which maps naturally to Dossify’s interval/activity summaries. [ActivityWatch architecture and export](https://github.com/ActivityWatch/activitywatch/blob/master/README.md) [ActivityWatch event model](https://docs.activitywatch.net/en/latest/buckets-and-events.html)
- **P0 — retain the native ActivityWatch source identity rather than assuming a universal schema.** Official examples distinguish `web.tab.current` payloads (`url`, `title`, `audible`, `incognito`), editor activity payloads (full file and project paths), window titles, and AFK state; timestamps are stored in UTC and the original offset is discarded. [ActivityWatch bucket/event schemas](https://docs.activitywatch.net/en/latest/buckets-and-events.html)
- **P0 — extend the existing Nextcloud provider from “files” to an incremental Activity adapter.** Nextcloud’s stable developer manual documents an Activity REST API with capability detection, ISO-8601 `datetime`, app/type/object metadata, pagination, and a monotonic `since` activity ID exposed through `X-Activity-Last-Given`; that is a stronger journal event source than inferring events from file mtimes. [Nextcloud Activity API](https://docs.nextcloud.com/server/stable/developer_manual/client_apis/activity-api.html)
- **P0 — support Nextcloud WebDAV and CalDAV/ICS as separate, conservative inputs.** Nextcloud lists WebDAV among its supported client APIs, and its OCS overview documents authenticated client requests and JSON negotiation. Google’s CalDAV guide describes CalDAV as the standard WebDAV calendar protocol, so an ICS/CalDAV-normalisation core can serve local Nextcloud calendars and optional Google calendars alike. [Nextcloud client APIs](https://docs.nextcloud.com/server/stable/developer_manual/client_apis/index.html) [Nextcloud OCS authentication](https://docs.nextcloud.com/server/stable/developer_manual/client_apis/OCS/ocs-api-overview.html) [Google CalDAV guide](https://developers.google.com/workspace/calendar/caldav/v2/guide)
- **P0 — make Immich a read-only metadata adapter, not a database or media-file parser.** Immich publishes OpenAPI documentation and generated TypeScript/Dart clients from its OpenAPI specification; it also says breaking API/deployment changes are intended to occur only in major releases. User API keys can be permission-limited. [Immich API](https://docs.immich.app/api/) [Immich versioning policy](https://docs.immich.app/install/upgrading/) [Immich CLI/API-key permissions](https://docs.immich.app/features/command-line-interface/)
- **P0 — add a generic archive intake layer with Google Takeout profiles.** Google confirms Takeout exports local archives for Calendar, Photos, YouTube, account activity and other selected products, and its formats include HTML, CSV, JSON, vCard and ICS-specialised formats. Dossify already has a `google_takeout` manifest entry, so the first improvement should be a versioned archive manifest plus parsers for Search/My Activity, YouTube history, Calendar ICS and Photos sidecars rather than a new cloud client. [Google Takeout export guide](https://support.google.com/accounts/answer/3024190)
- **P0 — add Apple Health XML and Google/Fitbit account-archive profiles.** Apple documents that Health can export all health and fitness data in XML. Google Health documents exporting an account archive containing Fitbit/Google health data such as activity, exercise, sleep and heart rate. These user-mediated archives are a better privacy fit than a continuously authorised health account. [Apple Health export](https://support.apple.com/en-ca/guide/iphone/iph5ede58c3d/ios) [Google Health/Fitbit export](https://support.google.com/googlehealth/answer/14236615)
- **P1 — improve the existing Navidrome integration only after verifying the installed server.** Navidrome’s documented Subsonic surface is compatible with API v1.16.1 and warns that a stream is not a play unless a scrobble with `submission=true` is sent. Navidrome says native scrobble/listen history starts only from version 0.59.0 and only records tracks added after that upgrade. [Navidrome Subsonic compatibility](https://www.navidrome.org/docs/developers/subsonic-api/) [Navidrome scrobble history](https://navidrome.org/docs/usage/scrobbling/)
- **P1 — use the stable Subsonic surface for Navidrome library metadata and only use its own v1 API after capability/stability inspection.** Navidrome’s own v1 documentation currently labels the API “work in progress” and not ready for implementation, despite serving an OpenAPI document; its published v1 reference attaches an operation-level stability designation. [Navidrome API v1 status](https://www.navidrome.org/docs/developers/api-v1/) [Navidrome v1 reference](https://navidrome.org/api/v1/)
- **P1 — make Jellyfin history an optional plugin-backed source, not a core dependency.** Jellyfin officially lists Playback Reporting as a plugin that can retain playback statistics, cull history, and manually query collected data. The plugin states that the collected information can be queried directly from the Jellyfin database, which is useful for a one-way local snapshot but is not a documented stable Dossify-facing API. [Jellyfin plugin catalogue](https://jellyfin.org/docs/general/server/plugins/index.html) [Playback Reporting repository](https://github.com/jellyfin/jellyfin-plugin-playbackreporting)
- **P1 — target documents, bookmarks and notes where a self-hosted service exposes a normal read API.** Paperless-ngx supplies a browsable, documented, versioned REST API; Karakeep has Bearer-token, cursor-paginated APIs for bookmarks, highlights, assets and backups; Memos provides Bearer-token REST/gRPC APIs with pagination. These can become small optional adapters for durable personal records, saved links and short notes. [Paperless API and versioning](https://docs.paperless-ngx.com/api/) [Paperless API-version contract](https://github.com/paperless-ngx/paperless-ngx/blob/dev/docs/api.md) [Karakeep API](https://docs.karakeep.app/api/karakeep-api/) [Memos API](https://usememos.com/docs/api/latest)
- **P2 — Home Assistant should be summary-oriented and retention-aware.** Recorder offers database-backed history, but its default retention is 10 days and automatic purge is enabled. Its include/exclude filters determine what enters the database at all, so unavailable old events are an expected data condition, not an importer error. [Home Assistant Recorder](https://www.home-assistant.io/integrations/recorder)
- **P2 — optional remote additions: Google Calendar and Strava.** Google Calendar has a least-privilege read-only scope and documented per-minute quotas. Strava provides a documented OAuth2 API for activity data, but access requires an app registration, has OAuth refresh-token handling and rates are enforced per application. [Google Calendar auth scopes](https://developers.google.com/workspace/calendar/api/auth) [Google Calendar quotas](https://developers.google.com/workspace/calendar/api/guides/quota) [Strava OAuth](https://developers.strava.com/docs/authentication/) [Strava rate limits](https://developers.strava.com/docs/rate-limits/)

### Inferences

- Implement a common **export-first adapter contract**: discover source/version, copy nothing, parse in place or a read-only staging directory, emit normalised facts with `source_id`, raw timestamp, parsed timezone, confidence and immutable input hash. It fits Dossify’s existing private configuration and makes Takeout, Apple Health, ActivityWatch JSON, ICS, GPX and future exports share provenance.
- The proposed order is: (1) ActivityWatch; (2) Nextcloud Activity plus ICS; (3) Immich metadata; (4) robust Google Takeout archive profiles; (5) Apple Health/Fitbit archives; (6) Navidrome/Jellyfin improvements; (7) Paperless/Karakeep/Memos; (8) Home Assistant; (9) Google Calendar/Strava OAuth. This order maximises local, user-controlled records before persistent third-party authority.
- Photo output should initially be lightweight facts only: capture/import date, album/ownership tags, asset ID and a local/Immich link. Do not copy images or run face/semantic search during a journal compilation; those operations expand both storage and sensitive-data exposure without being necessary to write a daily event.
- For browser/search history, prefer ActivityWatch’s explicitly collected browser events and the user’s Takeout archive. Direct reads of browser profile databases are not recommended as a cross-browser public adapter here because no stable, vendor-supported export/API evidence was found in this research.

### Gaps

- No official, stable Navidrome endpoint for retrieving complete native listen history was confirmed in the reviewed docs. Do not infer that the documented storage of history means the still-WIP v1 API can read it; require an installed-version capability test or a user-supplied export.
- No official Jellyfin playback-history REST/export endpoint was confirmed. The documented plugin/database route is installation-specific, so a Dossify adapter would need an explicit plugin-version/schema contract or a plugin-side JSON export.
- Matrix, Signal, WhatsApp and Telegram are deliberately not ranked: no primary, stable, privacy-preserving full-history import surface was verified in this pass. Treat user-produced exports as possible future archive profiles only after format-specific confirmation.

## Which open-source importer repositories or plugin ecosystems can inform implementation or be reused under compatible licenses?

### Takeaway

Use external projects chiefly as format/edge-case references and protocol test fixtures. Dossify presently has no top-level licence file in its checkout, so it should not copy any third-party code until its own licensing and attribution policy are decided; most relevant projects are reciprocal-copyleft, not drop-in reusable code.

### Cited Findings

- **ActivityWatch is the strongest implementation reference.** Its official repository exposes the event/export architecture and identifies the Python, JavaScript and Rust client libraries; the repository is MPL-2.0. MPL is file-level copyleft, so copying a source file requires preserving the applicable licence obligations, while independently written API client code is the cleaner route. [ActivityWatch repository and client libraries](https://github.com/ActivityWatch/activitywatch) [MPL-2.0 licence](https://github.com/ActivityWatch/activitywatch/blob/master/LICENSE.txt)
- **Immich offers an official generated SDK and OpenAPI schema, but its code is AGPL-3.0.** Consume the published schema or independently generate/implement a narrowly scoped client; do not transplant server/SDK code into Dossify without an AGPL compatibility decision. [Immich API/SDK generation](https://docs.immich.app/api/) [Immich licence](https://github.com/immich-app/immich/blob/main/LICENSE)
- **immich-go is valuable for Google Photos Takeout edge cases, not code reuse by default.** Immich itself recommends the community-maintained `immich-go` for Google Photos Takeout, and immich-go documents local archive ingestion, album handling, metadata sidecars and dry-run/continue options. Its repository is AGPL-3.0, so use it to establish fixture cases or invoke it as a user-chosen external migration tool rather than copying its parser. [Immich CLI recommendation](https://docs.immich.app/features/command-line-interface/) [immich-go Takeout examples](https://github.com/simulot/immich-go/blob/main/docs/examples.md) [immich-go licence](https://github.com/simulot/immich-go/blob/main/LICENSE)
- **Nextcloud is a protocol/reference source, not a code donor.** Nextcloud Server is AGPL-3.0, while its public developer documentation identifies OCS, Activity and WebDAV interfaces that Dossify can implement independently. [Nextcloud client API catalogue](https://docs.nextcloud.com/server/stable/developer_manual/client_apis/index.html) [Nextcloud licence](https://github.com/nextcloud/server/blob/master/COPYING)
- **Jellyfin’s Playback Reporting plugin already demonstrates the desired event capture but is GPL-3.0.** Reuse it operationally, or propose a read-only JSON-export endpoint upstream; do not import plugin classes into Dossify absent a GPL compatibility decision. [Playback Reporting README/licence](https://github.com/jellyfin/jellyfin-plugin-playbackreporting)
- **Memos is the exception worth inspecting for reusable client patterns.** The official Memos project exposes a public API and is MIT-licensed, subject to preserving its notice. [Memos API](https://usememos.com/docs/api/latest) [Memos licence](https://github.com/usememos/memos/blob/main/LICENSE)
- **Karakeep and Paperless-ngx are good API examples but reciprocal-copyleft codebases.** Karakeep’s AGPL-3.0 repository includes multiple importers and a documented REST API; Paperless-ngx has a versioned REST API but is GPL-3.0. Prefer direct HTTP clients and archive fixtures over source copying. [Karakeep repository](https://github.com/karakeep-app/karakeep) [Karakeep licence](https://github.com/karakeep-app/karakeep/blob/main/LICENSE) [Paperless-ngx API versioning](https://github.com/paperless-ngx/paperless-ngx/blob/dev/docs/api.md) [Paperless-ngx licence](https://github.com/paperless-ngx/paperless-ngx/blob/main/LICENSE)
- **Navidrome’s ecosystem is protocol-based.** Its client catalogue accepts applications implementing OpenSubsonic, Subsonic or Navidrome APIs, and Navidrome itself is GPL-3.0; a Dossify adapter can therefore be an independently implemented Subsonic reader rather than an embedded Navidrome component. [Navidrome client-app guidance](https://www.navidrome.org/docs/developers/adding-apps/) [Navidrome licence](https://github.com/navidrome/navidrome/blob/master/LICENSE)

### Inferences

- Create a fixture-only `research/fixtures` plan, never commit personal archives: synthetic ActivityWatch buckets; tiny, redacted Takeout directory trees; an Immich OpenAPI pinned schema; Nextcloud Activity JSON pages; ICS calendars; Apple Health XML; and mocked API pagination/rate-limit responses. This gains the learnings of the projects above without importing their code or private data.
- A reusable Python transport layer should be independently written around: file/archive iteration with zip-bomb limits; pagination/checkpointing; redaction-aware logging; and read-only HTTP. Provider modules should contain only mapping logic and schema/version validation.
- If Dossify later chooses an OSI licence, re-evaluate dependency choices then. Until that point, the safest legal/maintenance posture is “learn from, do not copy from” AGPL/GPL/MPL repositories; MIT Memos snippets are still better replaced by small independent code unless there is a concrete need.

### Gaps

- This review did not perform a legal compatibility analysis. A project licence for Dossify and each proposed code/dependency change must be reviewed before any code is copied or distributed.
- The examined projects do not provide a shared, maintained “personal journal importer SDK” with a permissive licence. A thin local adapter layer remains lower-risk than adopting a large importer framework.

## What privacy, OAuth, rate-limit, and data-loss risks should shape the integration order?

### Takeaway

The chief failure mode is not a parser crash but silently incomplete or over-collected personal history. Every adapter should be read-only, source-versioned, checkpointed, deduplicated by stable source IDs, and capable of reporting coverage gaps before it changes any generated journal block.

### Cited Findings

- **Takeout completeness is not instantaneous.** Google says a Takeout archive may omit changes made between export request and creation, has no date-range selection, may split archives, expires after about seven days and has a download limit. Those conditions require manifesting every part and reporting an explicit export cutoff rather than treating an archive as a live incremental feed. [Google Takeout limitations](https://support.google.com/accounts/answer/3024190)
- **Google Calendar remote access has a broad destructive scope available, even though read-only exists.** The official docs recommend the narrowest scope, distinguish `calendar.readonly` from the full scope that can edit/share/permanently delete calendars, and require verification for public apps using sensitive user-data scopes. [Google Calendar authorisation](https://developers.google.com/workspace/calendar/api/auth)
- **Google Calendar calls are rate-limited per project and per user; burst traffic can be rate-limited in the following sliding window.** The current published limits are 10,000 requests/minute/project and 600/minute/user/project, with exponential-backoff testing recommended. [Google Calendar quotas](https://developers.google.com/workspace/calendar/api/guides/quota)
- **Strava is an explicitly remote, policy-governed optional integration.** Its OAuth flow yields refresh and short-lived access tokens, and its API has 15-minute/daily limits with `429` on excess calls. Its policy says endpoints can be restricted, deprecated or removed. [Strava authentication](https://developers.strava.com/docs/authentication/) [Strava rate limits](https://developers.strava.com/docs/rate-limits/) [Strava API policy](https://www.strava.com/legal/api_policy)
- **Nextcloud is capable of more than Dossify needs.** OCS supports Basic authentication, session cookies and OIDC tokens, while the Activity feed includes user identity, subject/message text, object name/path and optional previews. An adapter must request/read only the activity/files/calendar data intentionally configured and must not log tokens or raw responses. [Nextcloud OCS authentication](https://docs.nextcloud.com/server/stable/developer_manual/client_apis/OCS/ocs-api-overview.html) [Nextcloud Activity response fields](https://docs.nextcloud.com/server/stable/developer_manual/client_apis/activity-api.html)
- **ActivityWatch can contain especially sensitive information.** Its official schemas include full URLs, page titles, full editor file/project paths and an `incognito` flag; timestamps lose their original timezone offset. Safe defaults should exclude incognito events, redact query strings/titles/paths unless an allow rule enables them, and state the assumed display timezone. [ActivityWatch schemas and timezone note](https://docs.activitywatch.net/en/latest/buckets-and-events.html)
- **Home Assistant histories can be intentionally incomplete and automatically purged.** Recorder’s default is daily automatic purge with `purge_keep_days: 10`, and include/exclude rules can prevent events from ever reaching the database. [Home Assistant Recorder retention and filtering](https://www.home-assistant.io/integrations/recorder)
- **Immich upgrades are not a safe opportunity to scrape internals.** Immich warns that downgrading is unsupported, has no backported patches, and intends breaking API/deployment changes at major versions; use the supported OpenAPI/API-key path and capture the server/API version in every run. [Immich versioning](https://docs.immich.app/install/upgrading/) [Immich API](https://docs.immich.app/api/)
- **Health exports need a stricter local-only class.** Apple’s full Health export and Google’s health archive include health/fitness data, so they should never be included in diagnostics, fixture archives, repository commits or remote telemetry. [Apple Health export](https://support.apple.com/en-ca/guide/iphone/iph5ede58c3d/ios) [Google Health export](https://support.google.com/googlehealth/answer/14236615)
- **Jellyfin data retention is configurable.** Playback Reporting can keep activity as long as desired or cull old information, so a Dossify reader must store coverage and plugin retention configuration with each ingestion rather than assuming a complete life-history. [Jellyfin Playback Reporting](https://jellyfin.org/docs/general/server/plugins/index.html)

### Inferences

- **Policy defaults:** disable all network adapters; require an explicit `allow_network = true` per provider; support only read scopes/keys; persist tokens outside the repository and outside verbose logs; expose a revoke/delete-token instruction in provider docs. For self-hosted services, prefer a dedicated read-only account/key or a read-only local snapshot when the server supports it.
- **Loss prevention:** make the first import dry-run and record source path, archive part hashes, parser version, source version, date coverage, count and warnings. On later runs, use stable identifiers/cursors but periodically re-scan a bounded overlap window to catch late-written records. Never delete source archives, server records or journal manual text.
- **Privacy filtering:** separate raw fact retention from display policy. Default to summaries (time totals, counts, domain/app categories) for activity/search/message/health sources; require positive rules before rendering URLs, search terms, message bodies, titles, locations, faces, file paths or health measurements.
- **OAuth order:** offer ICS/Takeout/manual export first; then a single-user local OAuth mode with narrow scopes and encrypted/local credential storage; defer multi-user/public OAuth because consent-screen verification, developer secrets, quota ownership and support obligations are materially different.

### Gaps

- No organisation-wide secret-storage mechanism or threat model for Dossify was supplied, so this research cannot recommend a concrete token store. The provider design should choose one before adding any OAuth adapter.
- No exact release/version ranges for the user’s deployed Immich, Nextcloud, ActivityWatch, Navidrome, Jellyfin or Home Assistant instances were supplied. Each adapter needs a startup capability/version check and a fixture set drawn from supported versions.
- No official rate-limit policy was identified for the local/self-hosted interfaces above; implement ordinary pagination, conditional requests where supported, and conservative retry/backoff instead of inventing limits.
