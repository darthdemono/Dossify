# Build Dossify Around Auditable Local Evidence

Dossify should become a **universal, local-first Markdown journal compiler**, not a replacement for an activity tracker, cloud health app, or SQLite-first personal-data warehouse. The strongest neighbouring projects divide the work in a useful way: Timelinize proves the value of importing heterogeneous personal archives with provenance and resumable jobs; ActivityWatch proves the value, and the sensitivity, of continuous local telemetry; and Open Life Tracker illustrates the different product created when accounts, cloud sync, and bidirectional health integrations become core features. Dossify already has the right product boundary: private TOML, identity and rules files select the inputs, while the engine writes only bounded auto-generated blocks and preserves manual journal text. The next step is therefore an **export-first fact pipeline** with typed adapters, versioned configuration schemas, plan-first dry runs, and source-linked deterministic Markdown projections. Start with user-controlled exports and read-only local services, then make remote OAuth an explicit exception. This path makes the journal more complete without making it less inspectable, portable, or private.

## Timelinize supplies the archive pattern while Markdown keeps authorship local

**Timelinize is Dossify's closest architectural neighbour, but not its storage model.** It imports heterogeneous records from files, devices, accounts, and applications; records them with sources, jobs, entities, relationships, checkpoints, and duplicate handling; and projects the resulting local index into timeline, map, conversation, entity, and media views. Its schema also acknowledges the awkward reality of personal data: entities imported from separate sources can duplicate and require reconciliation. That makes Timelinize an excellent reference for import manifests, resumable work, stable source IDs, and read-only projections, while its SQLite source of truth and its warning that upgrades can require timeline recreation show why Dossify should keep human-readable Markdown as the canonical journal. ([Timelinize import model](https://timelinize.com/docs/importing-data)) ([Timelinize schema](https://github.com/timelinize/timelinize/blob/main/timeline/schema.sql))

**ActivityWatch should be an upstream producer, not a capability Dossify absorbs.** Its local server stores source-specific buckets of UTC interval events, and watchers can record active applications, window titles, AFK status, browser URLs, page titles, editor paths, and an incognito flag. The same event store supports a dashboard, raw-data explorer, canonical-event queries, JSON export, and REST reads. That flexibility is valuable for Dossify only after a deliberately narrow transformation: retain the configured bucket and query provenance, aggregate intervals into a daily app/category or coding-time summary, and suppress titles, URLs, query strings, paths, and incognito events unless a positive private rule permits them. ActivityWatch itself cautions that its statistics are estimates and documents important same-host and multi-user security limits, so its raw telemetry must never become journal fact by default. ([ActivityWatch architecture](https://docs.activitywatch.net/en/latest/architecture.html)) ([ActivityWatch event model](https://docs.activitywatch.net/en/latest/buckets-and-events.html)) ([ActivityWatch security](https://docs.activitywatch.net/en/latest/security.html))

The closest verified project using the **Open Life Tracker** name is a Firebase-backed health PWA with Google Fit synchronisation, cloud-hosted per-user records, goals, charts, CSV export, and Telegram reports; its application source is private. It is useful evidence that health logs benefit from summaries and trends, but it is not a model for Dossify's architecture. Accounts, Firebase ownership, bidirectional sync, push-style reporting, and a cloud database would turn a compiler into an online personal-data service. Dossify should instead ingest a consciously supplied Apple Health XML or Google/Fitbit archive, render a reviewable health summary, and leave the original archive and manual journal in the owner's control. ([Life Tracker by Bonn](https://github.com/AndreaBonn/LifeTrackByBonn#technologies)) ([Apple Health export](https://support.apple.com/en-ca/guide/iphone/iph5ede58c3d/ios)) ([Google Health export](https://support.google.com/googlehealth/answer/14236615))

## A narrow typed adapter contract beats a universal scraper

The core should define a small, separately versioned `dossify_adapter_api`, then keep each provider responsible only for parsing and mapping its own records. A normalized fact needs a provider and adapter ID, source locator, native source-record ID or content hash, observed timestamp with timezone and precision, event type, structured values, display candidate, sensitivity/retention flags, and immutable input fingerprint. A private import manifest should record source version, archive-part hashes, adapter/parser version, coverage interval, parsed/skipped/duplicate counts, warnings, and checkpoint state. This preserves the provenance and repeat-import lessons of Timelinize and the flexible source-scoped event shape of ActivityWatch, while allowing Dossify to regenerate a daily Markdown projection deterministically whenever rendering rules change. ([Timelinize schema](https://github.com/timelinize/timelinize/blob/main/timeline/schema.sql)) ([ActivityWatch buckets and events](https://docs.activitywatch.net/en/latest/buckets-and-events.html))

For independently shipped adapters, **one PyPA entry-point group, `dossify.adapters`, is the right discovery boundary**. An installed package can advertise a provider slug and importable adapter factory, while the core owns compatibility checks and deterministically rejects duplicate slugs with both distribution names and versions in the diagnostic. PyPA entry points provide discovery and distribution identity, not a safe plugin protocol; loading one resolves Python code in Dossify's process, so installing and selecting an adapter remains a trust decision. Do not use entry-point extras as a dependency contract, and do not silently pick one provider where packages collide. ([PyPA entry-point specification](https://packaging.python.org/en/latest/specifications/entry-points/)) ([PyPA plugin discovery guide](https://packaging.python.org/en/latest/guides/creating-and-discovering-plugins/)) ([Python `importlib.metadata`](https://docs.python.org/3/library/importlib.metadata.html))

Pydantic should define the public request, result, configuration, manifest, plan, and diagnostic models, with checked-in Draft 2020-12 JSON Schemas generated from those models. Each `AdapterManifest` should declare provider ID, display name, supplying distribution/version, supported adapter-API range, config-schema version and `$id`, capabilities, requested permissions, deterministic-output status, and cache-contract version. Use JSON Schema for portable structural validation and Pydantic for semantic and cross-field validation: the JSON Schema `format` keyword is annotation by default, so it cannot be the sole security or provider-correctness check. Pydantic settings remain host plumbing, not the adapter interface, because unmatched environment variables can be ignored even when model extras are forbidden. ([Pydantic JSON Schema](https://docs.pydantic.dev/latest/concepts/json_schema/)) ([Pydantic Settings](https://docs.pydantic.dev/latest/concepts/pydantic_settings/)) ([JSON Schema validation](https://json-schema.org/draft/2020-12/json-schema-validation))

The execution contract should be **plan first, execute second**. `plan()` returns canonical JSON describing intended file reads, network requests without secret values, required permissions, output identifiers or content hashes where calculable, and cache action; `execute()` accepts only a core-issued plan ID. The core computes effective permission as the intersection of the user grant, adapter request, and command policy, then hands an adapter narrow facades such as a scoped reader, HTTP client, or secret resolver instead of raw filesystem, process, or global-settings access. In a dry run it calls only `plan()`, writes the plan and diagnostics, denies mutating capabilities, and changes no output or cache. This is least-authority protection against accidental overreach by a well-behaved adapter, not a sandbox for malicious in-process code; a real untrusted-plugin model would require a separate process and OS-level confinement. ([Python `importlib.metadata`](https://docs.python.org/3/library/importlib.metadata.html)) ([JSON Schema Core](https://json-schema.org/draft/2020-12/json-schema-core))

## Export-first providers produce the first valuable timeline

The integration sequence should favor records the owner has already exported or services they already operate locally. **ActivityWatch JSON/local REST, Nextcloud Activity plus ICS/CalDAV, Immich metadata, and versioned Google Takeout profiles form the first tier.** Nextcloud Activity has capability detection, pagination, ISO-8601 timestamps, and a monotonic `since` cursor, making it a better incremental source than filesystem mtimes; Immich exposes a supported OpenAPI surface and permission-limited API keys, so Dossify should emit asset dates, album/ownership tags, IDs, and local links without copying images or querying face/semantic data; and Takeout can consolidate Calendar, Photos sidecars, Search/My Activity, and YouTube history while remaining an owner-supplied archive. ([Nextcloud Activity API](https://docs.nextcloud.com/server/stable/developer_manual/client_apis/activity-api.html)) ([Immich API](https://docs.immich.app/api/)) ([Google Takeout export guide](https://support.google.com/accounts/answer/3024190))

| Priority | Adapter family | Dossify role and required boundary |
| --- | --- | --- |
| P0 | ActivityWatch; Nextcloud Activity/WebDAV/ICS; Immich; Google Takeout; Apple Health and Fitbit/Google Health archives | Parse export or explicitly configured local/read-only service into source-linked facts; render summaries by default and preserve archive/response provenance. |
| P1 | Navidrome; Jellyfin Playback Reporting; Paperless-ngx; Karakeep; Memos | Add only after a capability check, stable API/plugin-version contract, or user-supplied snapshot; treat documents, bookmarks, notes, and listening history as optional facts. |
| P2 | Home Assistant; Google Calendar OAuth; Strava OAuth | Keep disabled by default, report retention/coverage limits, request read-only scopes, and use conservative pagination and retry. |

Music needs unusual restraint. Navidrome's stable Subsonic compatibility surface is the safer place for library metadata, but its v1 API is still labelled work in progress, and native scrobble/listen history only begins with tracks added after version 0.59.0. Jellyfin Playback Reporting can retain and query activity, but the documented path is a plugin and database route rather than a stable playback-history REST API. Dossify should therefore preserve its present local integration only behind detected installed capabilities and add a normalized history adapter only when it has a versioned plugin export or a supplied snapshot. It must record the data's coverage and retention policy rather than treating a local history table as a complete life record. ([Navidrome Subsonic API](https://www.navidrome.org/docs/developers/subsonic-api/)) ([Navidrome scrobble history](https://navidrome.org/docs/usage/scrobbling/)) ([Jellyfin Playback Reporting](https://jellyfin.org/docs/general/server/plugins/index.html))

The same rule applies to self-hosted documents and notes. Paperless-ngx has a browsable, versioned REST API; Karakeep exposes cursor-paginated bookmark, highlight, asset, and backup APIs; and Memos has documented Bearer-token REST/gRPC APIs. They are good candidates for compact optional adapters because each has a normal read surface, but their outputs should be journal facts or source links, never a command to mutate the source service. Home Assistant belongs later because Recorder's default retention is only ten days and its include/exclude policy determines what ever reached history. For every partial source, “missing” must mean “outside recorded coverage” rather than “nothing happened.” ([Paperless-ngx API](https://docs.paperless-ngx.com/api/)) ([Karakeep API](https://docs.karakeep.app/api/karakeep-api/)) ([Memos API](https://usememos.com/docs/api/latest)) ([Home Assistant Recorder](https://www.home-assistant.io/integrations/recorder))

## Privacy and reproducibility turn collection into trustworthy memory

**The main risk is silent incompleteness or over-collection, not a failed parser.** The first run for every adapter should be a no-write dry run that creates an audit record of input path or endpoint, archive part hashes, server/parser version, coverage interval, record counts, warnings, and the canonical plan. Subsequent runs deduplicate with native IDs or content hashes, checkpoint paginated/archive work, and rescan a bounded overlap window for late-written entries. Core-owned cache keys must include canonical request, provider and distribution version, adapter-API/config-schema/cache-contract versions, redacted config hash, input fingerprints or ETags, compiler/target version, and permission scope. A changed key, reduced permission, explicit refresh, or failed validation invalidates reuse; a nondeterministic source declares itself so and disables cache reuse by default. ([Python `importlib.metadata`](https://docs.python.org/3/library/importlib.metadata.html)) ([Pydantic JSON Schema](https://docs.pydantic.dev/latest/concepts/json_schema/))

Privacy belongs in both the data contract and the renderer. Keep raw normalized facts in a private cache only when needed for reproducibility and diagnostics, then apply a separate display policy that defaults to totals, categories, and counts. Rendering a URL, search term, message body, title, location, face identity, file path, or health measurement requires an explicit allow rule; health exports never belong in fixtures, source control, telemetry, or verbose diagnostics. Disable network adapters by default, use read-only keys/scopes and dedicated low-privilege self-hosted accounts where available, keep credentials outside the repository and logs, and document token revocation. An OAuth route should arrive only after equivalent ICS, archive, or local options, initially as single-user local OAuth with the narrowest scope, not as a public multi-user integration with consent-screen, developer-secret, quota, and support obligations. ([ActivityWatch event schemas](https://docs.activitywatch.net/en/latest/buckets-and-events.html)) ([Google Calendar authorization](https://developers.google.com/workspace/calendar/api/auth)) ([Strava authentication](https://developers.strava.com/docs/authentication/))

External repositories should be treated as **specimens and fixture sources, not code banks**. ActivityWatch is MPL-2.0, Immich, Nextcloud, Karakeep, and immich-go are AGPL-3.0, Jellyfin Playback Reporting, Paperless-ngx, and Navidrome are GPL-3.0; each is valuable for protocol behavior, edge cases, and synthetic fixture design, but none should be copied while Dossify has no settled top-level licence and attribution policy. Memos is MIT-licensed and can inform a small client pattern, but independently written, narrow transport code remains simpler and safer. Build synthetic ActivityWatch buckets, redacted Takeout trees, tiny Apple Health XML, pinned Immich OpenAPI schemas, Nextcloud Activity pages, ICS calendars, and mocked pagination/rate-limit responses; never place an owner's export or identity data in the repository. ([ActivityWatch licence](https://github.com/ActivityWatch/activitywatch/blob/master/LICENSE.txt)) ([Immich licence](https://github.com/immich-app/immich/blob/main/LICENSE)) ([Memos licence](https://github.com/usememos/memos/blob/main/LICENSE))

The practical roadmap is four increments. First, refactor one existing in-tree adapter behind the typed fact/result models without changing the bounded Markdown write semantics, and establish fixture-based byte-for-byte deterministic output. Second, add archive manifests, the `plan()` artifact, provenance, private cache ownership, and the P0 export/local adapters; only then expose `dossify adapters doctor` and entry-point discovery for selected external packages. Third, introduce capability facades, effective-permission reporting, schema snapshot tests, duplicate-slug/API-range failure tests, and a versioned public adapter conformance suite. Fourth, add carefully scoped P1 adapters and local OAuth only after a secret-storage decision and provider-specific capability/version fixtures exist. Pluggy can later add host-owned lifecycle hooks for auditing or tracing, but it should not replace the one-provider `plan`/`execute` contract. ([Pluggy documentation](https://pluggy.readthedocs.io/en/latest/)) ([PyPA plugin discovery guide](https://packaging.python.org/en/latest/guides/creating-and-discovering-plugins/))

## Conclusion

Dossify can be universal without becoming totalizing: universality comes from a stable, private intermediate-fact and adapter contract, not from scraping every possible service or permanently collecting every signal. That changes the competitive frame. Timelinize-like archive breadth, ActivityWatch-like optional telemetry, and service-specific API adapters become replaceable evidence producers, while the journal remains an intelligible, owner-controlled compilation.

The most durable differentiator is an auditable boundary between evidence and prose. A versioned plan, coverage-aware provenance, redaction-first rendering, explicit permissions, deterministic regeneration, and tests built from synthetic fixtures let an owner answer not merely “what does my timeline say?” but “which local record made it say that, and what did the compiler deliberately leave out?”
